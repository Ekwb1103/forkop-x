# Forkop X / Rust X: интеграция Hot Reload, 2026-10-12

Изменения подготовлены локально на существующих main Forkop и Rust X. Релиз,
публикация и установка на клиентские роутеры не выполнялись.

## Реализованное поведение

Обычный Forkop reload теперь определяет поддержку Hot Reload по ответу
Rust X `/rust-x/applied-config`. Новый read-only CLI `reload-plan --current
<config> -c <candidate>` статически проверяет кандидат, сравнивает неизменяемые
части конфигурации и выдаёт SHA-256 обоих JSON. Проверка не поднимает второй
экземпляр ядра и не выполняет сетевую подготовку списков.

Forkop подготавливает конфиг и nftables до изменения рабочего состояния.
При совместимом изменении он устанавливает переходный nft guard, сохраняет
предыдущий конфиг, публикует кандидат и отправляет SIGHUP. Успех требует
подтверждения того же процесса (PID и start_ticks), нового поколения и точного
хеша кандидата. После проверки готовности Forkop завершает nft-транзакцию и
снимает guard. Секрет API передаётся curl через временный файл с правами 0600.

При ошибке старый конфиг возвращается и ядро должно подтвердить его новым
поколением. Если это невозможно, остаётся существующий путь восстановления с
контролируемой заменой процесса. Проверка поколения выполняется заново перед
каждым сигналом, включая откат конфига с уже видимым хешем.

При отсутствии возможностей нового Rust X или изменении слушателей сохраняется
прежний контролируемый restart. Интерфейс Forkop использует существующий reload;
отдельное действие в LuCI не требуется.

Также исправлен отсутствующий импорт `core.common` в обновлении подписок,
который вызывал Reference error при подготовке резервного конфига.

## Границы проверки

Hot Reload подключён к обычному lifecycle reload, включая списки и обычные
настройки DNS. Отдельные пути применения изменившейся подписки и автоматического
DNS failover пока сохраняют restart. Изменение слушателей также требует restart.
Brutal и WireGuard в эту доработку не включены.

Открытое TCP соединение проверялось через штатный direct-proxy SOCKS-вход;
сохранение длительного соединения через удалённый VLESS сервер отдельно не
измерялось. Краткий переходный nft guard может задерживать пакеты; отсутствие
смены PID не означает нулевую паузу в обработке всего трафика. OpenWrt 24,
ограничения памяти на 256 MiB и все узлы подписки в этом проходе не проверялись.

совпадают с сохранёнными до теста. Список установленных пакетов не изменился.
Временная подписка и её HWID-файлы удалены из рабочего состояния VM.
После восстановления файлов dnsmasq перезапущен для генерации активного

управляемый процесс ядра и DNS через 192.168.1.1: example.org → реальный IP,
example.com → исходная FakeIP политика.

## Повторная проверка совместимости и готовности canary

В дополнительном проходе проверен Sing-Box X 1.0.4 / upstream 1.14.2
(`1.14.2-x-1.0.4`) с финальными исходниками Forkop. Каталог заново прочитан
с нашего зеркала; проверены x86_64, идентичность пакета 1.0.4-r1, URL,
длина и SHA-256 скачанного amd64 executable archive. На VM временно
использован executable из этого архива, пакеты не устанавливались.
Архив: 9 791 916 байт,
SHA-256 `bb53a8cf317b13b584bfe7e4e30dd17f9b6377fbbcfb12b093fbafbb190736e7`.

Первый проход обнаружил дефект: `invalidate-list-cache` после применения
локального списка удалял JSON, на который уже ссылался рабочий config.json.
Запущенное ядро ещё держало список в памяти, но последующий check/restart
не мог открыть файл. Исправлено: этот вызов lifecycle использует
`preserve-runtime`, удаляя устаревший persistent cache и сохраняя рабочие
файлы. Явное полное инвалидирование продолжает удалять их. Добавлен тест
`tests/list_cache_runtime_preservation.sh`; пакеты после исправления пересобраны.
