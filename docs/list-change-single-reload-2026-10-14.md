# Изменение состава правил за один reload

Проверки 13–14 октября 2026 года (Europe/Moscow). Изменения находятся в
рабочем main Forkop; новый релиз с этим упрощением не публиковался.
Роутер 192.168.90.1 не изменялся.

## Реализация

- Изменение источников готовится синхронно внутри существующего reload lock.
  Используется прежняя транзакционная обработка списков в prepare-only режиме.
  Она не применяет nftables и не вызывает второй reload.
- Нужные исходные данные выбираются по URL и формату из текущего RAM-поколения.
  Размер, контрольная сумма и формат проверяются перед копированием.
  Flash-кеш используется при отсутствии RAM-манифеста; повреждённый источник
  нового RAM-поколения не подменяется старым flash-содержимым.
  Скачиваются только недостающие или повреждённые источники.
- Материализуется текущий состав списков. Удалённые и отключённые секции,
  а также удалённый последний список не оставляют прежних JSON-файлов.
  Пустое поколение разрешено при отсутствии обязательных источников.
- Пустая секция не меняет подпись источников. Cron-подпись зависит от наличия
  задач и интервалов, включая минимальный интервал подписок, а не URL и порядка
  секций. Неизменившийся crontab не записывается повторно; чужие задания сохраняются.
- Изменение конфигурации не переносит время последнего периодического
  обновления источников. Обновление по расписанию по-прежнему получает свежие
  данные, а не использует режим повторного применения кеша.
- Существующий снимок файлов списков удерживается до подтверждения core/nft
  перехода. При откате файлы восстанавливаются до HUP старой конфигурации.
  Подготовка кандидата, ACK ядра, временный nft guard и отказ с закрытием
  защищённого трафика при неуспешном восстановлении сохранены.

## Результаты

На Rust X 0.0.12 проверены локальные и настоящие HTTP-списки, обслуживаемые
временным uhttpd на loopback самой VM. После первой загрузки HTTP-сервер
выключен: добавление второго потребителя того же URL, удаление одного списка,
удаление последнего списка секции и отключение последней секции прошли
без доступного сервера. Повторное включение секции после удаления её данных
из активного поколения проверено с доступным сервером.

В итоговом прогоне:

- Семь изменений состава получили ровно один reload каждое.
- PID ядра 6028 сохранился. Поколения: 1 → 2 → 3, затем тестовый неуспешный
  apply и подтверждённый rollback 3 → 4 → 5, далее успешные изменения
  5 → 6 → 7 → 8 → 9 → 10.
- В каждом успешном применении API ready/hot_reload подтверждал новое
  поколение и канонический config_sha256, совпадающий с reload-plan текущего
  файла. Это канонический хеш конфигурации, а не SHA-256 её текстового файла.
- Инъекция FORKOP_HOT_RELOAD_FAIL_PHASE=after-apply при удалении HTTP-списка
  восстановила точные прежние JSON-файлы списков, конфигурацию и nft policy
  с тем же PID. Повторное применение успешно использовало готовое поколение
  без сети. После отката и успешных переходов guard отсутствовал.
- Добавление недоступного нового источника отклонено: PID, применённое
  поколение и файл конфигурации не изменились. Отмена этого редактирования
  также не меняла применённое поколение.
- DNS на 127.0.0.42 отвечал. Наличие и удаление материализованных файлов
  проверены отдельно. Продолжительность живых TCP/UDP-потоков не измерялась.

Фокусные проверки прошли:

- tests/list_change_cache.sh — повторное использование источников между
  секциями, удаления/отключение, один запрос нового URL, повреждённый кеш,
  отказ пустого манифеста при обязательных источниках, снимок для отката,
  интервалы подписок и отсутствие повторной записи cron.
- tests/list_update_reload_policy.sh
- tests/list_update_final_reload.sh
- tests/list_cache.sh
- tests/ruleset_required_reload.sh
- tests/rust_x_hot_reload.sh
- tests/community_subnet_routes.sh, включая материализацию из кеша.
- git diff --check.

Временные секции и HTTP-сервис удалены. Исходные UCI Forkop и sing-box
восстановлены: SHA-256 совпадают с состоянием до тестов.
VM оставлена с актуальными пакетами, работающим Forkop и прежними настройками.
Обе штатные проверки обновлений возвращают latest.

## Дополнение: Sing-Box X и повторный откат

На этой же VM временно установлен проверенный Sing-Box X 1.0.4-r1
(executable 1.14.2-x-1.0.4). Размер APK 9794164 байт, SHA-256
cdf5656a2d2e6a94ed6af05f91a12c854b0018aa917c0b8f317cc7daf42d756d;
пакет, архитектура и подпись проверены перед переключением.

В tests/ruleset_rollback_references.sh воспроизведён дефект кода тега 2.1.3:
подготовка конфигурации без прежнего списка удаляет его JSON/SRS файл, после
чего sing-box check прежней конфигурации завершается с no such file.
Текущий код сохраняет файл до успешного применения. Исправление ранней
очистки входит в 2.2.9-canary.8 (c0aa06b0) и последующие релизы.
Две строки пользовательского скриншота являются сообщениями об отказе
применения и отката; без предшествующих логов нельзя установить, был ли
именно этот дефект первичной причиной того события.

Для Sing-Box X проверен штатный путь с перезапуском ядра: семь изменений
состава прошли за один reload каждое, включая работу с выключенным сервером
списков. При двух последовательных инъекциях отказа применения nft оба
отката восстановили точную прежнюю конфигурацию и содержимое списков;
guard удалён, последующее применение прошло успешно, DNS отвечал.

Проверка повторного отказа выявила дополнительный случай в новом упрощении:
local list-content retry должен заново сохранить уже восстановленные файлы
перед их заменой. Добавлен snapshot-list-files для этого пути. Фикс проверен
на Sing-Box X; fixture проверяет создание снимка для повторной попытки.
Это дополнение относится к незавыпущенным изменениям рабочего main.

После завершения диагностики VM возвращена на исходный Rust X 0.0.12-r1.
Дополнительные прогоны после запроса пользователя прекратить их не запускались.
