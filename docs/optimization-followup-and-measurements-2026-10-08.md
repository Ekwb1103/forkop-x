## Уже сделано

1. Пропуск ожиданий отсутствующих провайдеров; при наличии PID-файлов прежние TERM/grace/KILL сохранены.
2. Удаление семи подтверждённых невызываемых функций и зависимости coreutils-base64 из упаковки, установщика и validator. Установленный пакет автоматически не удаляется.
3. Native fs.readlink для проверки процессов без ослабления provenance, start_ticks и deleted executable checks.
4. Native ожидание завершения команды версии с deadline; отказ и частичный вывод не принимаются.
5. Валидация неизменившихся SRS по SHA-256 с повторным использованием успешного parser proof, миграцией старых markers и обычным parsing изменённых данных.
6. Один snapshot успешного определения версии в пределах подготовки подписок и один запрос вместо двух в init_config.
7. DNS reload с проверкой config/instance/process/socket/protocol readiness, bounded ожиданием и fallback restart в поддерживаемой области. Восстановление DNS между stop/start сохранено.

Порог 8 секунд оставлен по решению пользователя. Sing-Box X не обновлялся в ходе этой оптимизации. Упаковка backend в bytecode, минификация LuCI и урезание X не внедрены.

Рекомендуемый следующий небольшой этап: проверка транзакции списков и удаление пустой заглушки/остатков snapshot, актуализация shell inventory, затем отдельный проверенный кандидат минификации LuCI. Ни один из этих пунктов не оправдывает обещание ещё нескольких секунд ускорения полного restart.

Не удалять миграции, распознавание Tiny/ordinary/Extended, package rollback, bind-dig, arbitrary JSON protocol support, QUIC sniffing/blocking, SRS parser для новых данных, последний рабочий кэш, nft transition guard и восстановление DNS. Удаление исходников некомпилируемых Go-модулей не уменьшает установленный executable.

### Изолированные подтверждения

* Пустые ожидания: на обеих ВМ исходные контрольные restart около 18,3–19,6 с, кандидат около 12,5–12,6 с. Простая политика без реальных подписок/активных провайдеров. Это не полный manual_restart пользовательского роутера.
* Native readlink: на роутере проверка конфликта процессов 0,69–0,72 → 0,09–0,10 с. Повторные проверки объясняют, почему выигрыш всего lifecycle превышает выигрыш одного сканирования.
* Version deadline: check-requirements на роутере 1,10 → 0,51 с. Уменьшение конкретного этапа подтверждено даже при более медленном полном запуске.
* Восемь неизменившихся SRS: первая миграция legacy markers 5,62 с, последующие refresh 1,14–1,18 с; новые данные требуют parser. Не обещать этот выигрыш первому запуску или каждому cold boot.
* DNS в последнем сопоставлении: restore/configure сумма 5,77 → 1,14/1,21 с. Старый эксперимент около 0,8 с не имел финальной строгой readiness-проверки и не является временем установленного helper.
* Весь init-config на последнем этапе 2,76 → 4,57/3,54 с из-за вариации sing-box check 0,82 → 3,10/2,07 с; сам generator около 0,44/0,43 с. Поэтому нельзя писать «генерация конфигурации ускорилась с 3,6 до 0,43 с»: это разные границы измерения.
* Version snapshot убрал подтверждённые повторные запуски executable; один такой вызов около 0,43 с на этом роутере. Сеть подписки около 0,15–0,17 с, семи остальных списков около 0,61 с; ограниченный параллелизм не введён.

### Исключить из итогового сравнения

21,66 с — экспериментальный внутренний restart с исследовательским DNS reload, без полной подготовки данных. 6,3 с — эксперимент ВМ с пустыми ожиданиями и порогом 2 с, который не выбран для production. Эти времена нельзя представлять как текущую скорость полного ручного перезапуска.

Обе ВМ функционально прошли reboot текущего backend, а ранее отдельно подтверждено сохранение SRS parser proof после reboot. Парного полного boot baseline/after нет. Uptime 26,35/41,39 с в последней проверке — моменты наблюдения через SSH, не boot-ready duration. Пользовательский роутер не перезагружался.
