# Реальный flash и RAM: X → Tiny → X на 192.168.90.1

7 октября 2026, примерно 22:05–22:12 МСК. Проверка на личном роутере пользователя с разрешённым временным переключением сборок. Итог: рабочий sing-box X 1.0.1-r1; экономия writable flash против Tiny — **22 096 KiB = 21,578125 MiB**. Экономия RAM не подтверждена.

## Среда и исходное состояние

- GL.iNet GL-MT6000, ARM64, mediatek/filogic, aarch64_cortex-a53; APK сообщает базовую архитектуру aarch64 и принимает выбранный cortex-a53 APK.
- OpenWrt 25.12.5 r33051-f5dae5ece4, ядро 6.12.94.
- Весь тест: backend, LuCI и перевод Forkop **2.0.0_rc1** (2.0.0-canary.1). Forkop не обновлялся.
- `/overlay`: `/dev/loop0`, **F2FS**, 7 581 184 KiB; `/` — overlayfs; `/tmp` — tmpfs.
- `/rom`: SquashFS, 6 144 KiB, read-only. Файлов sing-box в `/rom` не найдено. Алгоритм сжатия SquashFS не установлен: источник mount `/dev/root` отсутствует как доступный device node.
- `/sys/fs/f2fs/loop0/features`: `pin_file`; `/sys/fs/f2fs/loop0/feature_list/compression`: **unsupported**. В mount options нет compression. Сжатие writable FS не является объяснением измеренной разницы.
- При первом подключении пакет sing-box, бинарник и init-скрипт отсутствовали, но процесс PID 25246 ещё работал с удалённым executable. Активной пакетной транзакции не обнаружено. SHA-256 `/proc/25246/exe` совпал с извлечённым X 1.0.1 из зеркала. Это состояние не использовано как baseline; проверенный X восстановлен и сервис перезапущен перед X1.

## Одинаковая конфигурация и метод

Одинаковые пользовательские настройки **UCI**, одна версия Forkop. Побайтно одинаковый runtime JSON для разных ядер не использовался: Tiny 1.13.21 отвергает DNS action `evaluate` из X/1.14 JSON. Forkop штатно генерировал совместимый JSON после установки каждого ядра. Поэтому это сравнение одной пользовательской конфигурации, а не эксперимент с идентичным JSON двух версий sing-box.

Перед каждым переключением сохранялось состояние пакетов и сервисов. Forkop останавливался, конфликтующий core удалялся, точный новый APK устанавливался offline, без package scripts. Восстанавливались UCI и ранее работавший init; запуск выполнялся через Forkop. В тестовом скрипте предусмотрен возврат X при ошибке перехода.

После каждой установки: `sing-box check`, работающий процесс, Clash API `/version`, разрешение DNS и настоящий HTTPS через существующий SOCKS inbound `192.168.90.1:2080` (Google generate_204, HTTP 204). Все три точки прошли. Извлечённые preview и созданные установками `.apk-new` убраны; defaults сохранены в tmpfs. APK-архивы X/Tiny сохранены именно как rollback, не на flash. Неиспользуемые тестовые APK старого X удалены в конце.

После `sync` — ожидание 10 секунд и пять отсчётов через 10 секунд с повторным `sync`. Для X2 добавлены три отсчёта после стабилизации. Никакой принудительной очистки системного cache или посторонних файлов не выполнялось.

UCI совпадали при проверке переходов. В конечном работающем состоянии Forkop изменил штатный служебный `shutdown_correctly`; после исключения только этой строки SHA-256 исходного и конечного Forkop UCI совпадает (`c34b259918d7a16e6da3e34f6ec1d572fff3fac7edb1fc8a02ca1f47aa8bc851`). Sing-box UCI совпадает полностью. Сравнение исходного X JSON и конечного X выявило лишь перестановку 20 элементов одного selector; множество узлов совпало.

## Flash

Все значения `df` и `du` ниже — **KiB**, размер файла — байты.

| Метрика | X1: 1.0.1-r1 | Tiny: 1.13.21-r1 | X2: 1.0.1-r1, стабильно |
|---|---:|---:|---:|
| Бинарник, байт | 8 537 372 | 31 137 064 | 8 537 372 |
| `du` бинарника, merged и upper | 8 348 | 30 440 | 8 348 |
| `du -sk /overlay/upper` | 121 431 | 143 523 | 121 431 |
| `df /overlay` used | 322 480 | 344 576 | 322 480 |
| `df /overlay` available | 7 258 704 | 7 236 608 | 7 258 704 |
| `du /etc/sing-box` | 44 | 44 | 44 |
| `du /usr/share/sing-box` | 4 658 | 4 658 | 4 658 |
| `du /var/cache/apk` (tmpfs) | 1 528 | 1 528 | 1 528 |

X1 и Tiny: все пять `df` совпали. X2: первые три отсчёта used=322 488, затем 322 480; ещё три финальных отсчёта подтвердили 322 480. Первые лишние 8 KiB не включены в стабильную разницу. Инвентари `du -ak /overlay/upper` X1 и конечного X2 совпали полностью. Hash всех APKINDEX в tmpfs-cache до/после совпал.

Разница логических размеров бинарников — **22 599 692 байта = 22 070,0117 KiB**. Разница их `du` — **22 092 KiB**; разница общего `df` — **22 096 KiB**. Таким образом, почти вся реальная экономия совпадает с освобождённой аллокацией бинарника. Около 22 KiB сверх логической разницы отражены в самом файловом учёте `du`; ещё 4 KiB — разница глобального учёта `df`. Инвентарь Tiny также показывает изменения APK metadata и небольшие различия аллокации некоторых уже существующих файлов; их суммарный эффект на `du upper` компенсировался. Приписывать эти байты конкретному механизму без дополнительных filesystem-level измерений нельзя.

Абсолютное used всего F2FS нельзя отождествлять с суммой размера одного бинарника или `du upper`: `df` учитывает весь раздел и filesystem accounting. Постоянная разница этих двух показателей в парном тесте сокращается. Неизменяемый `/rom`, сохранённые зависимости, rollback и cache не дали ложной экономии flash.

## RAM

`/proc/PID/smaps_rollup` недоступен; использованы `VmRSS`, `VmHWM`, `RssAnon`, `RssFile`, `RssShmem`, `/proc/meminfo`. VmSize около 1,3 GiB — виртуальное адресное пространство, не фактическая RAM.

| RSS, KiB | Наблюдение |
|---|---:|
| X1, пять чистых отсчётов | 53 408–53 488 |
| Tiny, пять отсчётов | 48 920–49 012 |
| X2, первые пять отсчётов | 48 772–49 772 |
| X2, три дополнительных отсчёта после ожидания | 52 428–52 444 |

Поздний X2 против последнего Tiny: **+3 432 KiB ≈ +3,35 MiB RSS**, а не экономия. Первое X против Tiny давало до +4,37 MiB. После ещё одного финального HTTPS запроса RSS X вырос до 53 092 KiB. RAM меняется с временем и реальной нагрузкой; это наблюдение работающего роутера, а не доказательство фиксированного расхода на одинаковом replay трафика.

Последний Tiny: anon=22 804, file=26 084, shmem=124 KiB. Поздний X2: anon=41 084, file=4, shmem=11 356 KiB. В maps X обнаружен `/memfd:upx (deleted)`: распакованный исполняемый код живёт в RAM. Маленький UPX-файл на flash не означает пропорционально меньший RSS. File-backed страницы Tiny и anonymous/shmem страницы X также различаются по возможности reclaim. Из этих значений нельзя вывести точную экономию системной RAM только вычитанием MemFree/MemAvailable: остаются buffers, file cache, kernel memory и посторонний трафик.

В пяти точках Tiny MemAvailable=718 824–720 908 KiB, X1=691 060–694 792 KiB, X2=686 256–695 648 KiB. Это сырой общий показатель, не изолированный core delta. Тестовые rollback и backup находились в tmpfs; их footprint отдельно наблюдался. После удаления двух ненужных старых X APK тестовый каталог занимает 22 324 KiB tmpfs, общий `/tmp` used=56 916 KiB. Их удаление не изменило `df /overlay`.

## Расчёт установщика

**Действующий компонентный preflight на роутере** (`/usr/lib/forkop/components/action.uc`, сохранённая копия в artifacts) использует `installed-size` extracted APK payload: X=8 539 655 байт / 8 340 KiB, Tiny=31 139 443 байта / 30 410 KiB. Payload содержит UPX-packed X, не его 28 836 002-byte plain executable. Это верный исходный размер для flash.

Для replacement: максимум target/rollback, по 5% + 2 048 KiB запаса, минус credit 75% проверенного writable бинарника; `/rom` credit не получает. Существующие зависимости сохранены. Проверен настоящий preflight fixture установленного кода:

| Переход | Свободно flash, KiB | Требует flash | Writable credit | Rollback payload | Требует tmp |
|---|---:|---:|---:|---:|---:|
| X → Tiny | 7 258 700 | 27 726 | 6 252 | 8 340 | 16 530 |
| Tiny → X | 7 236 608 | 11 173 | 22 805 | 30 410 | 38 600 |

Числа взяты из реального `logread` (`Sing-box preflight passed`). Разница 4 KiB в первом available относится к моменту до очистки тестового X `.apk-new`. В обеих транзакциях запас был огромным. На этом несжимаемом F2FS модель flash корректна и консервативна; 8/30 KiB превышения аллокации над payload укладываются в запас. Эти цифры — требуемое дополнительное свободное место для безопасного перехода, а не прогноз конечного `df used`. Тест с изобилием свободного места не проверяет каждый сценарий near-full FS или сбоя питания.

**Shared `install.sh` в локальном checkout** содержит отдельную проблемную ветку. `forkop_install_required_space_kb()` объясняет множитель archive×2 утверждением, что OpenWrt compresses writable overlay. Для этого роутера утверждение неверно; универсальную корректность модели не подтверждает.

Кроме того, low-space fallback Tiny (`install.sh:2605`) считает `ceil(archive_KiB × 1.25) + 512`: для выбранного APK **13 942 KiB**, при измеренном `du` одного бинарника **30 440 KiB**. Занижение уже относительно одного бинарника — **16 498 KiB ≈ 16,11 MiB**. На малом несжимаемом overlay это может разрешить переход без необходимого места. Эта ветка в нашем тесте не запускалась; вывод получен из действующего исходника и точного проверенного APK, а не из аварийного заполнения роутера.

Новая X-планировка shared installer (`prepare_sing_box_x_plan`, строки 2849–2870) уже использует metadata `installed_size + 3%`, что согласуется с измерениями. Итого: компонентный payload-preflight здесь прошёл корректно; считать **все** расчёты установщика корректными нельзя из-за архивной Tiny fallback ветки и недостоверного обобщения о writable compression. Код установщика в рамках диагностики не изменялся.

## Конечное состояние и доказательства

X 1.0.1-r1, executable `1.14.2-x-1.0.1`, Forkop 2.0.0_rc1, procd running=true (PID 16419), API сообщает X, DNS и HTTPS через SOCKS прошли, used/available `/overlay`=322 480/7 258 704 KiB. Пользовательские настройки сохранены.

Несекретные raw outputs, пакеты, копия проверенного action.uc, скрипты измерений и файловые инвентари: `artifacts/router90-flash-20261007/`. Секретные runtime/config backups остались только в закрытом каталоге роутера. В repository ничего не коммитилось.
