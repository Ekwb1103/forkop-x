# Проверка Tachyon 1.5.4–1.5.6 для Forkop X

Дата: 2026-10-11. Проверены три последних публичных релиза через GitHub API,
их release notes и исходный diff `1.5.3...1.5.6`. Сопоставление с текущим
локальным main Forkop и `artifacts/tachyon-core` (Rust X 0.0.7).
Незакоммиченные изменения сохранены. Код, пакеты, VM и службы не менялись.
Это статическая проверка: перечисленные дефекты не воспроизводились на VM.

Источники:

- https://github.com/Dushnilin/tachyon/releases/tag/1.5.4
- https://github.com/Dushnilin/tachyon/releases/tag/1.5.5
- https://github.com/Dushnilin/tachyon/releases/tag/1.5.6
- https://github.com/Dushnilin/tachyon/compare/1.5.3...1.5.6

## Что требуется обновить

### 1. Сохранять протокол при извлечении ruleset в nftables

Приоритет высокий. `routing/rulesets.uc:collect_ip_cidr_nft_outputs()`
сохраняет IP и порт, но не `network`. Затем
`nft/apply.uc:nft_add_json_ruleset_subnets_for_section()` кладёт результат в
общие `sets.ip_ports` / `sets.ip6_ports`. Эти наборы проверяются и для TCP,
и для UDP. Поэтому правило `network=udp + ip_cidr + port` получает также
TCP-классификацию, которой в исходном ruleset нет.

Tachyon 1.5.5 добавляет частный случай: чистые UDP ruleset с портами направляет
в `udp_ip_ports` / `udp_ip6_ports`. Для Forkop лучше адаптировать извлечение
с разделением TCP/UDP; частный upstream guard не решает смешанные и логические
ruleset. Существующую обработку Discord и порядок секций сохранить.

Проверки: UDP-only, TCP-only, смешанные правила, IPv4/IPv6, диапазоны портов,
логические AND/OR и ограничения секции. Проверять отсутствие лишнего TCP
совпадения, а не только наличие UDP-записи.

### 2. Закрыть недостающий случай чистой установки sing-box

Приоритет высокий. `singbox/runtime.uc:ensure_sing_box_main_section()` уже
есть, но вызывает `core/uci.uc:set_section()`, который возвращает false,
если `load()` не смог загрузить отсутствующий `/etc/config/sing-box`.
Таким образом, наличие помощника ещё не покрывает отсутствие файла.

Также `configure_service()` не создаёт workdir, а встроенные init-шаблоны
в runtime.uc, components/action.uc и config/validator.uc используют
`/usr/share/sing-box` без его создания.

Адаптация 1.5.5: создать отсутствующий конфиг перед его загрузкой, обеспечить
рабочий каталог, сохранить существующие пользовательские настройки.
Проверить реальный отсутствующий UCI-файл, а не только fixture-курсор.
Для каждого core/package варианта учитывать наличие каталога в пакете.

### 3. Защита DNS failover на время загрузки ядра

Приоритет средний. В `singbox/dns_failover.uc:worker()` нет проверки возраста
или готовности ядра: активные пробы начинаются сразу. При трёх неудачных
проверках возможна смена резолвера и перезапуск ещё загружающегося ядра.
Tachyon 1.5.4 откладывает пробы на первые 90 секунд и сбрасывает счётчики.

В Forkop адаптировать с учётом управляемого procd PID и DNS readiness,
не копировать выбор первого `pidof` и предположение о 100 тиках в секунду.
Проверить медленный старт, отсутствие ядра, смену PID и восстановление
резолвера после периода загрузки. Это риск по коду; цикл на Forkop не измерен.

### 4. Распространить проверку readiness на обновление подписки

Приоритет средний. Forkop уже имеет более строгий помощник
`service/state.uc:wait_managed_sing_box_config_listeners()` — проверяет
mixed-сокеты и принадлежность единственному управляемому процессу.
Он используется в lifecycle.uc, но `components/updates.uc:
subscription_update_common_locked()` после замены ядра проверяет лишь
`start-managed-sing-box-runtime`, который подтверждает PID/ownership,
а не готовность слушателей. Затем стартует DNS failover.

Использовать существующую readiness-проверку в этом пути, предусмотрев
конфигурации без mixed-inbound: сейчас помощник возвращает false при пустом
списке. Проверять необходимые DNS/TProxy/TUN ресурсы по конфигурации.
Tachyon 1.5.4 закрывает похожую проблему после SIGHUP, но Forkop применяет
контролируемую замену процесса. Переносить SIGHUP ради сохранения PID не нужно:
это не доказывает сохранение соединений.

### 5. Точная диагностика лимита GitHub API

Приоритет средний/низкий. `components/action.uc:http_get_once()` использует
curl `-f`, а функции получения GitHub releases не сохраняют HTTP-код и тело
ошибки. Ответ о лимите неотличим от сетевого отказа.

Адаптировать статус, тело, заголовки reset/retry и backoff в GitHub-пути.
Сценария обхода десятка зеркал из Tachyon здесь нет: Forkop выполняет
proxy/direct попытки. Публикации X и Rust X продолжать получать через наши
проверяемые зеркальные каталоги.

## Что не требуется переносить сейчас

- 1.5.6: `buffer_size` / `flush_interval` не генерируются Forkop; ошибка
  загрязнения конфигурации этими полями отсутствует. Не включать их по
  числовой версии Rust X или Sing-Box X: это разные проекты и версии.
- В .uc исходниках Forkop нет `(?:`; исправление несовместимых regex
  из 1.5.5/1.5.6 уже не требуется.
- Автоудаление произвольных неизвестных полей из 1.5.6 не переносить вслепую:
  Forkop отклоняет невалидный generated config. Возможная будущая адаптация
  должна быть ограничена известными необязательными полями и временным
  candidate config; не терять незаметно параметры безопасности/маршрутизации.
- Smart Detect, Telegram bot settings, серверный менеджер/экспорт FPTN,
  AWG/WireGuard, Strategy Fuzzer и AI Doctor отсутствуют в текущем Forkop.
  Их исправления не являются исправлениями наших существующих функций.
- FPTN существует в исходниках Rust X, но отдельного FPTN provider/action
  в Forkop нет. Upstream gate внешнего fptn-client сейчас неприменим.
- Пагинация компонентов и ручной GitHub tag — отдельное расширение UI,
  не обязательный bugfix. Forkop selector уже использует releases.json.
  Для X/Rust X произвольный тег не должен обходить зеркальный manifest,
  проверку architecture/package/revision, размера и SHA-256.
- Русскую локализацию Tachyon нельзя оценивать как покрытие Forkop:
  разные каталоги и наборы функций.

## Нужен ли новый релиз ядра

Нет установленной необходимости по этим трём релизам. Это релизы приложения
`Dushnilin/tachyon`, а не `Dushnilin/tachyon-core`. Перечисленные применимые
изменения относятся к управляющему коду Forkop и не требуют изменений
Sing-Box X (Go) или Rust X (Rust).

Рекомендуемый порядок небольших задач: протоколы ruleset → чистая установка →
готовность ядра/DNS failover → GitHub backoff. Сборка и публикация релиза
не выполнялись; runtime-совместимость этих будущих изменений ещё не проверена.

## Реализация по последующему запросу пользователя

Все пять применимых доработок внесены в локальный main:

- Извлечение ruleset разделяет TCP/UDP, включая вложенные AND/OR и ограничения
  портов секции. Общие элементы остаются общими; правила с одним транспортом
  идут в соответствующие IPv4/IPv6-наборы. TCP/UDP-цепочки создаются и без
  Discord. Инвертированные выражения не превращаются в положительные IP-наборы.
  Временные транспортные файлы удаляются после обновления.
- core.uci создаёт отсутствующий конфиг эксклюзивно перед созданием секции;
  ошибочный или существующий файл не перезаписывает. configure-service
  создаёт сохранённый custom workdir или дефолтный каталог. Три init-шаблона
  также обеспечивают workdir перед запуском.
- Readiness проверяет владельцев объявленных mixed/HTTP/SOCKS TCP, direct/TProxy
  TCP/UDP-сокетов. Для явно именованного TUN проверяет интерфейс и fdinfo
  управляемого процесса. Конфигурация без mixed корректно обрабатывается;
  отсутствующий/невалидный конфиг отклоняется.
- Обновление подписки ждёт readiness до старта вспомогательных workers. При
  ошибке генерации, запуска или готовности возвращает сохранённый runtime
  config и проверяет восстановление. Если восстановление не удалось,
  приватная резервная копия остаётся доступной по указанному в логе пути.
- DNS failover не накапливает отказы и не выполняет recovery-пробы первые
  90 секунд наблюдения управляемого PID/start_ticks. Отсутствие или смена
  процесса сбрасывает наблюдение и счётчики. Время монотонное; пересчёт
  /proc ticks в секунды не используется. Это намеренная задержка после
  старта самого worker даже для уже работающего ядра.
- GitHub API сохраняет HTTP-код, тело и заголовки, различает обычный 403,
  429, primary/secondary rate limits. X-RateLimit-Reset и числовой Retry-After
  определяют ограниченный backoff, сохранённый в runtime state. Зеркальные
  каталоги собственных ядер не затронуты.

### Проверки выполнены

Временные исходники и тесты размещались только в
`/tmp/forkop-tachyon-improvements` на двух существующих VM. До тестов сохранены
package/service state и хеши UCI. Никакие пакеты не устанавливались и не
обновлялись; службы не останавливались. Изменённые установленные модули не
подменялись.

На OpenWrt 25 и OpenWrt 24:

- Все 12 затронутых/new ucode-модулей скомпилированы штатным VM-компилятором.
- tachyon_improvements.sh: настоящий изолированный libuci cursor,
  отсутствующий/существующий/повреждённый конфиг, custom workdir; TCP/UDP
  readiness planning, monotonic grace и политика GitHub; actual HTTP-path
  с fake curl и сохранённым backoff.
- ruleset_transport_nft.sh: UDP-only/TCP-only, IPv4/IPv6, диапазоны,
  ограничения секции, вложенные AND/OR и распределение портов по транспорту;
  nft candidate и реальный `nft -c` без применения. Проверено, что временная
  таблица после check-only не появилась в live firewall.
- subscription_runtime_readiness.sh: отсутствующий TCP/UDP, чужой PID,
  race смены PID; faulted generation/start/readiness, recovery failure,
  восстановление старого config и порядок запуска workers.
- dns_failover_startup_grace.sh: actual worker loop с подставным временем,
  сменой/отсутствием процесса и отказами DNS; пробы и накопление strikes
  не начинаются в grace-периоде.
- Прошли существующие netstat_listener_owner.sh, community_subnet_routes.sh,
  nft_atomic_apply.sh, automatic_latency_pending.sh.

На OpenWrt 25 дополнительно прошли native_process_identity.sh,
sing_box_runtime.sh и list_update_reload_policy.sh (bash отсутствует на VM24).

Новая readiness-функция успешно проверила live config без перезапуска на
обеих VM: Rust X 0.0.7 на VM25 и Rust X 0.0.3 на VM24. Это проверка текущих
сокетов и ownership, не полный end-to-end тест новой установленной сборки.
Настоящий TUN-процесс и реальные GitHub rate limits не провоцировались.

После тестов package lists, полный ubus service state с PID и оба UCI-хеша
совпали с исходными на обеих VM. Полный nft hash менялся на работающих VM;
первичная фиксация не исключала счётчики, поэтому доказательством неизменности
структуры firewall этот hash не является. Тесты применяли только candidates
и check-only validation. git diff --check прошёл.

Код ядер и версии не изменены; release/build/publication не выполнялись.
