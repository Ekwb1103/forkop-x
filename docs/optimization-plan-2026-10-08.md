Работа на существующей main. Сохранять незакоммиченные изменения. Этот план не запускает публикацию или выпуск новых версий. Порог стабильности core остаётся 8 секунд; DNS recovery, transaction rollback и проверки ownership сохраняются. Пользовательский роутер не reboot; reboot на двух существующих ВМ.

## Точка отсчёта

Актуализация после выполнения: пакетная установка/точный откат/переустановка и переход со старого canary проверены на обеих ВМ; LuCI Save & Apply с реальным изменением имени прошёл и конфигурация восстановлена. Весь осторожно компактный JS и backend cleanup установлены на роутере. DHCP helper перенесён и проверен. Подробности, текущие APK hashes и границы проверки: optimization-plan-stage2-2026-10-08.md. Ниже сохранена исходная точка планирования; она не описывает текущий installed state.

На пользовательском роутере установлен предыдущий оптимизированный backend: последние полные manual_restart 29,92/28,98 с. Минификация main.js и последняя очистка candidate-кода пока только в working tree и локальных пакетах 2.0.0. Проверены frontend tests/typecheck/AST/build, source overlay на ВМ и восстановление оригиналов; полноценные browser UI и package install/upgrade последнего этапа ещё впереди.

Измеренные размеры и границы проверки — package-size-cleanup-2026-10-08.md. Хронология restart — optimization-followup-and-measurements-2026-10-08.md. Не суммировать выигрыши отдельных несопоставимых запусков.

## 1. Завершить проверку уже подготовленного кандидата

* Проверить реальную загрузку LuCI на обеих ВМ: dashboard, настройки, секции, сохранение, переводы, мониторинг и RPC. AST equivalence не подменяет browser UI test.
* Проверить установку/повторную установку и обновление APK/IPK, согласованность backend/LuCI/i18n, сохранение UCI, working runtime и точный откат. Не считать VM source overlay пакетной проверкой.
* После VM checks сохранить на пользовательском роутере exact rollback пакеты/состояние, сообщить о воздействии, установить проверенный локальный кандидат и проверить UI, DNS, SOCKS HTTPS и one-core runtime. Ядро X не менять.
* Критерий завершения: файлы и package accounting совпадают, frontend/runtime работают, откат проверен, production profiling fixtures отсутствуют.

Размерный эффект уже подтверждён: main.js −100137 байт (97,79 КиБ), LuCI APK −10816 байт. Уборка updates.uc −473 байта. Новое ускорение restart этим этапом не обещается.

## 2. Довести простые изменения размера и архитектуры

* Минифицировать section.js и остальные ручные LuCI-файлы на этапе сборки/упаковки, сохранив readable source, require directives, top-level return и экспортируемые имена. Оба способа упаковки должны давать одинаковый результат.
* Перенести DHCP detection из install.sh в подходящий helper; проверить отсутствие helper на старой/повреждённой установке, fallback и cleanup после неудачного обновления. Не удалять проверку ради installer_owner.
* Повторить проверку ссылок перед удалением других функций. Не трактовать несколько одноимённых функций из разных модулей как один implementation owner.
* Критерий завершения: frontend/typecheck/build/UI, installer regression старой и новой установки, package artifacts и source/payload sizes.

Старая оценка общего JS выигрыша около 150 КиБ; примерно 98 КиБ уже реализовано. Для остатка разумный ориентир около 50 КиБ файлов, но нужен свежий замер. Архитектурная правка установщика не имеет подтверждённого размерного или временного выигрыша.

## 3. Отдельный кандидат stripped bytecode backend

* Составить matrix фактических версий ucode и loader на OpenWrt 24/25, проверить сборочный ucode против runtime. Не считать одно успешное compile подтверждением переносимости всех версий/архитектур.
* Упаковывать библиотечные .uc модули в bytecode; shebang entrypoint и shell package hooks обрабатывать отдельно. Исходники оставить в Git. Согласовать build.sh и OpenWrt Makefile.
* Проверить чистую установку, обновление со старой версии, migrations, runtime commands, process/DNS failure, rollback и reboot обеих ВМ. Затем проверить ARM64 на пользовательском роутере с exact rollback, без reboot.
* Проверить обслуживание: diagnostics, sourceless traceback, воспроизводимость сборки и возможность восстановить предыдущий текстовый backend.
* Критерий завершения: все выбранные runtime environments принимают payload; recovery не зависит от несовместимого bytecode; размер измерен в payload и на устройстве.

Свежий size experiment: 68 модулей, 1877848 байт текста → 1340836 байт bytecode; разница 537012 байт (524,43 КиБ). Это размерный кандидат, не доказанный выигрыш времени или RAM. В предыдущем эксперименте заметного ускорения restart не было.

Уточнение matrix: этот старый WSL bytecode имеет version 0x00 и отвергнут всеми тремя native runtimes, требующими 0x01. Отдельная native 0x01 сборка: 1342632 байта, экономия 535216 байт; loader/read commands прошли на обеих ВМ и ARM64. Packaging, failure/reboot и совместимый воспроизводимый host compiler остаются до внедрения. Bytecode не установлен в production.

## 4. Тестовые входы и legacy, не затрагивая рабочую совместимость

* Инвентаризировать fixture CLI/helper-функции и места их использования. Вынести тестовые входы из production payload так, чтобы тесты по-прежнему проверяли реальные production algorithms.
* Не выбрасывать совместимость Tiny/ordinary/Extended, UCI migrations, транзакционный rollback, provider shutdown, QUIC sniffing/blocking и arbitrary JSON протоколы как «legacy».
* Верхняя старая оценка fixture функций около 40 КиБ текста. После bytecode их размерный эффект нужно измерять заново, он не складывается с 524 КиБ напрямую.

## 5. Новый точечный runtime profile

Это исследование после безопасной упаковки, не заранее заявленное ускорение:

* Выяснить вариацию sing-box check: в последнем профиле 0,82 → 3,10/2,07 с. Разделить CPU/UPX startup, память, IO и конкурирующих workers. Проверку JSON не пропускать и не выполнять параллельно с resident core без memory evidence.
* Разделить остаточную координацию подписок: UCI/locks, чтение существующего cache, selection request profiles и метаданные. Убирать только доказанные повторы в пределах одной операции, без долгоживущего stale cache.
* Оценить повторный local import списков: последний профиль около 0,66 + 0,52 с. Возможное повторное использование требует корректной invalidation и сохранения atomic nft/runtime generation.
* Проверить количество запусков ucode/helper и повторных чтений в конкретных горячих участках. Объединять вызовы только при сохранении command status, ownership и failure propagation.
* Сеть подписки около 0,15–0,17 с, семи остальных списков около 0,61 с на измеренном наборе. Поэтому параллелизм низкого приоритета; не ожидать от него нескольких секунд выигрыша на этом наборе.

Критерий принятия: воспроизводимый выигрыш конкретной фазы, отсутствие роста peak RAM и сохранение отказного поведения. Итоговый temporal gain пока не оценён; 8 секунд стабильности не сокращать.

## 6. Корректное завершение и cold boot

* Исследовать отсутствие STOP/K-link и предупреждение unclean shutdown. Проверить реальный shutdown path, порядок Forkop/dnsmasq/network и procd transaction.
* Исправлять orderly shutdown, если подтверждён дефект; не скрывать warning и не добавлять STOP вслепую.
* Reboot matrix на ВМ: обычный reboot, delayed WAN, отсутствующий DNS upstream, ограниченная RAM и прерванный startup. Проверять DNS между загрузкой dnsmasq и готовностью core.
* Сравнивать boot от одинаковой точки, например uptime Linux до подтверждения runtime/DNS, отдельно от BIOS/SSH polling. Старые моменты наблюдения 26,35/41,39 с не baseline boot duration.

Это прежде всего надёжность. Ускорение cold boot не обещается до парного измерения.

## 7. Sing-Box X — отдельный необязательный этап

X уже собран с Go -s -w и UPX -9. ARM64 executable 8,14 МиБ, x86_64 9,41 МиБ. Повторная упаковка UPX как самостоятельная оптимизация не нужна.

* При необходимости исследовать minimal CLI profile, не меняя доступные прокси-протоколы: старый эксперимент −99512 байт ARM64 / −117580 байт x86_64 после UPX.
* Более сильное UPX compression исследовать только на исходном ELF, с integrity/RAM/startup checks; выигрыш не известен.
* Сокращение протоколов и замена bind-dig не входят в простой безопасный этап. bind-dig используется текущим DNS readiness/failover, а arbitrary JSON поддержка может использовать редкие протоколы.
* Любое изменение X требует отдельного package identity/revision, проверенного mirror catalog и component rollout. Не объединять его с backend update автоматически.

| Уже подготовленный main.js + cleanup | около 98 КиБ | Измерено; LuCI APK уменьшается только на 10,56 КиБ |

Fixture cleanup не добавлять к bytecode простым сложением. Эти числа не являются прогнозом освобождённых physical flash blocks, уменьшения RAM или размера архивов. Payload, APK/IPK и writable filesystem нужно показывать отдельно.

По скорости базовая точка — последние 29,92/28,98 с полного manual_restart; исходный instrumented профиль 43,56 с уже включал первый этап. Следующие размерные изменения могут вообще не ускорить restart. Дополнительное ускорение будет определено этапом 5; обещание 20 или 15 секунд на текущих данных необоснованно. Точные baseline/after сравнения делать серией чередующихся запусков на одинаковой конфигурации, фиксируя cache/network conditions и median/range, без суммирования вложенных таймеров.
