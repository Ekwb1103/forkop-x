# Уборка временных файлов и кэша смены ядра

Изменения в локальном main, без установки или публикации пакетов.

- При записи идентичности нового ядра запоминается путь кэша кандидата.
  После ошибки action_fail удаляет только эту БД, если возврат к прежнему
  runtime подтвержден readiness и его cache_file.path совпадает с сохраненным.
  Неуспешное восстановление сохраняет кэш и recovery-пакеты. Общий путь
  внутри семейства не удаляется.
- Каталоги новых updater-операций содержат .forkop-owner. Уборка по TTL
  сохраняет живых владельцев. Каталоги с .forkop-recovery, rollback-пакетами
  или forkop-backup сохраняются; незавершенное восстановление не теряет данные.
  Каталоги без recovery удаляются спустя 30 минут при следующем updater-вызове.
- Точные staging-файлы /usr/bin/sing-box.forkop-new.PID и
  /usr/lib/libcronet.so.forkop-new.PID удаляются спустя 10 минут только
  при отсутствующем процессе владельца. Ссылки, каталоги и другие имена
  не затрагиваются. Старые standalone HTTP/command файлы также учитывают
  живого PID и владельца глобальной блокировки.
- Рекурсивная уборка временного каталога не следует по symlink.

Это уборка при очередной операции, а не новый фоновый таймер.
Recovery-данные могут занимать место до разрешения сбоя; автоматически
удалять их по возрасту небезопасно. Исторические диагностические каталоги
и чужие файлы не сканируются. Всеобщая гарантия отсутствия накопления
или утечки памяти не заявляется.

На существующей OpenWrt 25 VM (25.12.5) в отдельном /tmp-каталоге прошли
component_storage_cleanup.uc и sing_box_cache_identity.uc. Проверены
реальные файлы/каталоги, TTL, живой/отсутствующий PID, recovery-маркер,
backup, блокировка другой/текущей операции, symlink и сохранность активной БД.
components/action.uc скомпилирован ucode. До/после пакеты и procd service
list совпали. Реальный пакетный переход и SIGKILL updater не воспроизводились.

## Последующая реальная интеграционная проверка

По запросу пользователя выполнены мутационные тесты на существующей
VMware VM OpenWrt 25.12.5 (192.168.1.1). До теста сохранены пакетное
состояние, службы, исходные lib/init/UCI/runtime config. Для теста управляющий
код временно установлен на VM, cache_path направлен в отдельный /tmp-каталог.

Первый реальный fault-тест выявил дефект: configured_runtime_cache был
объявлен до используемой as_string и в ucode возвращал пустой путь.
Помощник перенесен после as_string; добавлен runtime-cache-path-fixture
и тест вызова реального components/action.uc с отдельным UCI fixture.

Подтверждено после исправления:

- Rust X 0.0.7 → Sing-Box X 1.0.4: после запуска X и создания настоящей
  cache.db (32768 байт) init-wrapper вернул 42. Updater восстановил точный
  Rust X 0.0.7-r1, работающий runtime/DNS и удалил БД кандидата.
- Успешный Rust X → X; затем X 1.0.4 → Rust X 0.0.8: updater подтвердил
  readiness, прежняя X БД удалена, DNS example.com работает через FakeIP.
- Повторен fault-тест на окончательном коде Rust X 0.0.8 → X → rollback.
  Recovery-маркер существует еще до старта кандидата; БД кандидата удалена.
- Настоящий updater остановлен SIGKILL во время запроса каталога (до
  пакетных мутаций). Пока PID был жив, устаревшие тестовые каталог и
  staging-файл на /usr/bin сохранялись. Следующий реальный updater-вызов
  удалил их; отдельный recovery-каталог сохранился. Возраст тестовых
  файлов был выставлен в прошлое; ожидание 10/30 минут не требовалось.
- Добавлен .forkop-recovery перед первой мутацией смены ядра, чтобы
  SIGKILL внутри транзакции не позволил TTL убрать rollback-пакет.
  Legacy-каталоги без owner-маркера с APK/IPK также сохраняются.

Пакеты загружены с зеркала через штатный updater с проверками manifest,
архитектуры, package identity, размера и SHA-256. Для окончательного возврата
Rust X 0.0.7-r1 APK отдельно сверены manifest, x86_64, размер, метаданные и
SHA-256 b1ab6aa6812a5b306bdb492cbda40ed6a0c4053d05db8fd3d385d779de3bf447.
SIGKILL непосредственно внутри apk не тестировался: проверены раннее
создание recovery-маркера и сохранение такого каталога уборкой.

После тестов восстановлены исходные Rust X 0.0.7-r1, управляющий код,
init и UCI/runtime config. Список пакетов до/после совпал. Сравнение
исходных action.uc/generator.uc/ruleset_cache.uc побайтовое; добавленные
тестовые модули удалены с VM. SHA-256 /etc/config/forkop и runtime config
совпали с исходными. Финальный статус running=1, dns_configured=1,
example.com разрешается через FakeIP 198.18.0.2. Перезапущенные службы
имеют новые PID; побайтовое совпадение procd service list не ожидается.
Логи сохранены в tmp/storage-live-verification/evidence.tar.gz в workspace.
Временный тестовый каталог с VM удален после сохранения результатов.
